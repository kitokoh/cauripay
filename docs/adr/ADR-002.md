# ADR-002 — Le cœur produit est la plateforme wallet GOURSI ; le v0.1 (agrégateur) sort du périmètre actif

- **Statut** : Proposé → **Accepté** (2026-08-14)
- **Décideur** : Responsable projet (à valider par le propriétaire)
- **Issues** : GOURSI-ADR1 (#267), EPIC-G0 (#153)

## Contexte

Le dépôt contient un agrégateur v0.1 (API type Stripe, checkout, simulateur) dont la roadmap visait
v0.2–v0.4 (vrais PSP, SDK, payouts…). La spec GOURSI redéfinit le produit : **plateforme wallet
complète** (comptes, ledger double écriture, agents, marchands, KYC/AML, USSD, mobile).

## Décision

1. **La cible est la plateforme wallet GOURSI** (backlog #138–#271).
2. **L'agrégateur v0.1 est conservé en historique** : `legacy/` (server, dashboard, docs v0.1).
   Il n'est ni amélioré ni exploité en production.
3. **L'ancien backlog (#1–#137 : connecteurs, SDK, payouts, multi-utilisateurs, mode live, etc.) sort
   du périmètre actif** : les besoins qu'il exprimait sont re-couverts par le backlog GOURSI
   (rails → GOURSI-030, webhooks → GOURSI-031/026, SDK → GOURSI-051, KYC/AML → GOURSI-024/025,
   ledger/réconciliation → GOURSI-012/033, mode live → GOURSI-050, déploiement → GOURSI-005).

## Conséquences

- Les issues #1–#137 sont **closes avec un commentaire de supersession** pointant vers l'équivalent GOURSI.
- Les éventuels enseignements (design webhooks HMAC, idempotence, registres devises) sont **réutilisés**
  dans les nouveaux services.

## Alternatives écartées

- Faire évoluer l'agrégateur vers la plateforme : dette structurelle (SQLite → Postgres, Fastify → NestJS,
  pas de ledger), coût supérieur à une refonte en monorepo.
- Supprimer le v0.1 : perte d'historique et de références utiles (registres, conventions webhook).
