# ADR-005 — Événement transaction.completed : ledger ET api-core, déduplication par transactionId

- **Statut** : Proposé → **Accepté** (2026-08-14)
- **Décideur** : kitokoh (propriétaire) — arbitrage demandé par GOURSI-ADR1 (#267)
- **Issue** : GOURSI-ADR1 (#267) — bloc G2

## Contexte

Le ledger publie la vérité comptable (`financial.events/transaction.completed`) après commit ; api-core
publie un événement **enrichi** (walletIds, type, métadonnées métier) pour les consommateurs qui ont
besoin du contexte. Sans arbitrage, deux événements pour la même transaction = risque de double
traitement (notification en double, réconciliation faussée).

## Décision

1. **Ledger** publie `transaction.completed` (payload minimal `{ transactionId, type, amount, status,
   walletIds }`) — vérité comptable, après commit uniquement.
2. **api-core** publie un événement enrichi sur le même exchange avec le **même `transactionId`**.
3. **Tous les consommateurs dédupliquent par `transactionId`** (stockage des IDs vus — Redis/table) :
   le premier événement reçu est traité, le second est ignoré (idempotence de consommation).
4. La déduplication par transactionId s'applique aussi à `transaction.reversed` et `transaction.failed`.

## Conséquences

- Chaque consommateur (reconciliation-service, notification-service, business-service) implémente un
  filtre idempotent par transactionId.
- Le ledger garde la vérité comptable ; api-core porte le contexte métier. Aucun événement supprimé.
- Coût : logique de déduplication à écrire une fois dans un helper partagé (`packages/shared-types` ou
  module commun des consommateurs).
